Formal verification of Bitcoin's consensus rules

thebitcoincommons.org

The method

ExtractUsed AI to extract Bitcoin Core's consensus rules in full — signature validation, UTXO accounting, script execution, block structure — and expressed them as a formal mathematical proof. That document is the Orange Paper.
ImplementBuilt an alternative implementation in Rust derived entirely from the Orange Paper, not from Core's source code.
Differential testing and fuzzingRan both implementations against the same mainnet history and generated inputs. Every divergence triggered an amendment to the implementation, the proof, or both, until the two converged.
Spec-lockTied the implementation to the Orange Paper using Z3 SMT provers and a custom AST. The lock is language-agnostic — it could be applied to any implementation targeting the spec. A change that breaks a consensus property fails the build before it reaches review.
AI review layerDeployed a product trained specifically on Bitcoin to review every pull request for conformance with Bitcoin's mission, constraints, and purpose. Consistent review, not dependent on who is available.

What a written spec reveals

Theorem 6.2.3 in the Orange Paper proves total supply converges to exactly 21 million BTC. The Rust function carries #[spec_locked("6.2")]. On every merge, Z3 checks the code still satisfies the theorem.

The implementation was correct. The spec wasn't describing what the implementation was actually doing.

The total supply is not exactly 21 million BTC. It's 20,999,999.9769 BTC. Block subsidies use integer division, so every halving drops fractional satoshis. Those fractions accumulate to about 0.023 BTC short of the cap. We corrected the theorems to reflect what the math actually produces. The implementation didn't change.

Also: Bitcoin doesn't target a 10-minute block time. The retarget formula measures 2,015 intervals across a 2,016-block window. The actual target interval works out to 600.3 seconds, not 600.

The part worth arguing about

  1. When an independent implementation and Core disagree on whether a block is valid, which one is wrong, and how would we know?
  2. How much specification is enough? Machine-checked proofs, or is a precise human-readable document the thing that does the real work over fifty years?

Status, plainly: the specification is real and published. BLVM v0.1.47 is in active development, not a battle-tested deployment. Governance is written but cryptographic merge enforcement is off.
